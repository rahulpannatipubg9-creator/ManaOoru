# Phase 1 architecture audit

Read-only source audit of the current checkout, 27 October 2026. This document is the only file changed for this audit. No full-world run, performance measurement or regression execution was performed. File presence is not treated as runtime integration.

## Runtime entry and source of truth

`project.godot` starts `scenes/main.tscn` using GL Compatibility on desktop/mobile. The scene instances `World`, the on-foot person, several rigid-body cars, a helicopter and a tuk-tuk. `scripts/main.gd::_ready()` coordinates control authority, spawn placement, HUD, route graph, GPS, map binding and vehicle-entry transitions. It is the existing composition root; extending it incrementally is safer than replacing it.

`scripts/map/geo_projection.gd` is the coordinate authority: Chowrastha 79.513352 E / 18.751925 N; +X east, −Z north; 1 world unit/metre; 3,000 m playable radius. Keep projection, map labels, terrain, spawn selection and navigation in this common frame.

`MapData.load_shared()` caches a parsed projected map. Its loader combines core/features OSM, curated reference places/pins, user shop exports, Microsoft footprints, optional Vidya Nagar 2 Overture buildings and local signals, then creates `TerrainData` and `BuildingHeights`. Geographic provenance exists separately from procedural appearance. Never reclassify decorative variations as surveyed buildings or businesses.

## Implemented and connected

| System | Current implementation and evidence | Boundaries/risks |
|---|---|---|
| World generation | `world_generator.gd::_ready()` builds terrain, `RoadBuilder`, `BuildingBuilder`, signs, water infrastructure, bus station, billboards, CCTV, fountain, coal gallery, street life, trees, birds, pedestrians, local activity, traffic and coins. | Many systems build synchronously during scene startup; no measured start-up/frame budget claimed here. |
| Terrain | `TerrainData.height_at()` interpolates the same grid triangles as the terrain mesh. `_create_ground()` makes chunked terrain geometry and concave collision, with visible terrain slightly below its collision reference. | Coarse DEM is not a street-engineering survey. Separate visual/collision offsets must remain intentional. |
| Roads/map areas | `RoadBuilder.build()` builds source roads, draped 7.5 m segments, markings, shoulders, crossing details and map areas into 250 m chunks. Road surface collision uses layer 2 for classification; world physics also relies on terrain and solids. | Render widths can be inferred by road style/lanes; they are not cadastral edges. Road-layer classification and physical collision are distinct. |
| Buildings/storefronts | `BuildingBuilder.setup()` preserves source footprints and metadata; `_style_for()` chooses deterministic appearance and measured/fallback heights. `apply_source_appearance()` accepts explicit source color/height/levels. `StorefrontAllocator` constrains named signs to reviewed frontage units. | Appearance and many facade details are representative. Do not replace real footprints with generic models to hide gaps. Unassigned signs/places are not proof of missing physical shops. |
| Streaming/rendering | Buildings use 160 m chunks, nearest-first pending jobs with 4 ms nominal per-frame work budget, synchronous `build_around()` at spawn/Vidya Nagar 2, shared shader and tank MultiMeshes. Visibility range is 900 m desktop/550 m mobile. Trees use 96 m chunks, 3 ms budget and near/far representations. Street furniture uses shared/chunked meshes. | Building visibility cutoffs are not geometric LOD. `MeshSurface.to_mesh()` creates one surface without explicit LOD index arrays. Built building chunks retain collision/resources; they are not unloaded merely because invisible. |
| Player/control | `person.tscn` uses `person_controller.gd` plus the `test_character.gd` visual child. Character has camera-relative movement, acceleration, jump/crouch, slope/step handling, recovery and impact/health logic. `GameplayControls` gates owner/context and clears held input. | Preserve control ownership, diagonal normalization, idle stability, touch/keyboard parity and UI focus guards. Weapon display is implemented; its export explicitly says no firing. |
| Cameras/vehicle entry | `camera_controller.gd` owns orbit, touch look, spring-arm clipping, first/third person and chase behavior. `vehicle_entry.gd` handles entry transitions; `main.gd` selects authority and camera target. | Do not couple body rotation to camera yaw or introduce transform teleports into rigid-body driving. |
| Vehicles | Active car scenes use `rigid_vehicle.gd`: raycast suspension, wheel contact and friction-circle forces, drivetrain/gearbox/audio; helicopter has its own controller. `main::_place_on_real_roadsides()` grounds and settles vehicles. | `scenes/player/player.tscn` still uses legacy kinematic `player_controller.gd` and is used by tests/labs; it is not the main scene's car implementation. Audit both when modifying shared drivetrain contracts. |
| Ambient traffic/pedestrians | `TrafficBuilder` creates visual route followers; `TrafficVehicle` updates along routes/signals and samples ground. `LocalActivityBuilder` creates bounded shop visitors, bus passengers and crossing routines; `pedestrian.gd` handles gait/contact. | These are lightweight ambient routines, not city-scale crowd navigation or the player's rigid-body driving model. Do not infer collision fidelity from visual movement. |
| GPS/maps | `RoadNetwork` builds an OSM-node-connected graph, walk/drive flags, costs/components and snapping; `GpsNavigator` samples progress at 0.2 s, reroutes and reports arrival. Main wires HUD minimap/full map to the same projected dataset and rendered footprints. | Never connect geometrically crossing roads that lack a shared source node; bridges and ground roads may be separate. Route reachability is not door-to-door pedestrian routing. |
| Basic interactions | Main's on-foot interaction enters nearby vehicles, otherwise buys at `LocalActivityBuilder` shops for one HUD coin, or shows bus-terminal information. Coin collection and wallet operations are connected. | A purchase hint is not an inventory, shop interior or persistent economy. No connected mission manager/delivery state machine was found. |

## Present but dormant, optional or contradictory

**CityLife is currently dormant in normal startup.** `main.gd` preloads `CityLifeController`, declares `city_life: Node3D`, and has guarded journal/weather/shop/save hooks. Its `_ready()` does **not** instantiate, add or call `setup()` on it. `scenes/main.tscn` does not attach it either. Consequently `city_life.gd`'s inventory/energy/fuel, discovery targets, achievements, journal/modals, versioned atomic JSON persistence, `city_shop_interior.gd`, `city_environment.gd`'s day/night/weather/audio and `city_community.gd`'s added community routines are implemented modules but not active main-scene features. Static lighting configured directly in main is active instead. Do not tell players that F5/F6, persistent progress or interiors work in this checkout without wiring and testing them.

`tests/city_life_regression.gd` assumes `game.city_life` exists and dereferences `life.save_enabled` before its non-null check. It cannot serve as evidence of successful current integration. Prior screenshots/reports can represent a different code state.

**Drainage remains active by default despite the user's stop request.** `world_generator.gd` still instantiates `RoadsideDrainage` unless launched with `--no-drainage`. The builder describes representative scenery, not surveyed GIS. Separately `RoadBuilder.ENABLE_INFERRED_DRAINS` is false, and `drainage_demo.tscn` is standalone. Removing or disabling the default builder is a distinct product-policy correction; do not mistake the legacy flag for disabling all drainage. No TGRAC import call was found in normal startup.

`BuildingBuilder.USE_DECORATIVE_HOUSE_MODELS` and `ENABLE_INFERRED_RESIDENTIAL_FORECOURTS` are false; house/apartment model-fit code and forecourt helpers therefore are not current city output. `shop_marker_loader.gd` exists but no attachment/reference was found in the inspected main-scene/script tree. Standalone tests/labs do not imply these features are enabled for normal play.

## Safe priorities before feature expansion

1. Establish a small runtime smoke/assertion test around the actual main composition root: expected modules, active control owner, HUD/map binding and clean teardown. Decide explicitly whether CityLife is enabled; either integrate it once with a guarded lifecycle or present its modules as future work. Fix the test's null-check order alongside integration.
2. Honor the no-drainage decision at the default entry point and keep restricted research assets outside build resources. Maintain source/appearance evidence and current OSM/Microsoft/other asset attribution documented in `ASSET_LICENSES.md`.
3. Define one short neighborhood street as a visual acceptance fixture: fixed cameras, lighting/time/weather, grounded pedestrians/tyres, signs/entrances, shade readability. Do not expand inferred scenery to compensate for missing real map records.
4. Measure start-up cost, frame-time spikes, chunk memory/collision retention, draw calls and transparency on the M1/mobile profile before adding more assets. Bounded existing builders are preferable to per-building Nodes/materials or new dependencies.
5. Add objectives through a separate small mission state module using existing GPS and interaction interfaces, with explicit save versioning if persistence is enabled. Avoid overloading the existing map loader or vehicle controller.
6. After gameplay edits run the required movement regression plus focused camera, entry, navigation, suspension, grounding and relevant city-module checks. Existing tests are useful inventory, not proof they currently pass. Report unavailable checks honestly.

This audit does not certify legal rights, positional truth, physical simulation accuracy, performance targets or production readiness; it records the inspected code connections and the smallest safe next steps.
